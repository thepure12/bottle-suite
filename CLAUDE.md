# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bottler is a Python package (`bottler`) that bundles several `bottle.py` plugins — CORS, REST resources, JWT auth, and SQL/SQLite — into a single `Bottle` subclass (`Bottler`), plus a CLI to scaffold and run projects, and an optional Vue/Nuxt admin dashboard.

The package vendors these small single-module `bottle.py` plugins directly under `src/bottler/plugins/` (originally standalone PyPI packages by the same author, now maintained in-repo, re-exported via `plugins/__init__.py`):
- `plugins/rest.py` — provides `API` (the REST plugin, `self.rest`) and the `Resource` base class
- `plugins/jwt.py` — provides `JWTPlugin` (`self.jwt`) and `authFunc`
- `plugins/sql.py` — provides `sqlitePlugin`/`sqlPlugin` (`self.sqlite`/`self.sql`)
- `plugins/cors.py` — provides `CorsPlugin` (`self.cors`)

## Commands

Install for local dev (editable):
```bash
python3 -m pip install -e .
```

Run tests (unittest, run from repo root — every test module starts with `import _paths` to idempotently `os.chdir` into `tests/`, so discovery order doesn't matter):
```bash
python3 -m pip install -e ".[test]"     # adds coverage + webtest as test deps
python3 -m unittest discover -s tests -v
python3 -m unittest tests.test_bottler -v
python3 -m unittest tests.test_bottler.TestBottler.test_genResoursesForDB -v
make test                                # = coverage run -m unittest discover -s tests -v && coverage report -m
```
Tests require `webtest`, `toml`, `PyJWT`, `pymysql`; the sqlite path is exercised for real against `tests/resources.db`/`tests/bottler.toml`, while MySQL-only branches (no live MySQL server assumed) are exercised by mocking `pymysql.connect` via `tests/mysql_mock.py`. `[tool.coverage]` in `pyproject.toml` scopes measurement to the core package (`core.py`, `resource_factory.py`, `resources.py`, `plugins/*.py`, `dashboard/resources/token.py` — excludes `src/bottler/cli/` and the Nuxt client) with `fail_under = 100`; the suite currently holds 100% branch coverage there. See "Testing" under Architecture for suite structure and fixture-isolation gotchas.

Build/publish (`Makefile`). Every upload passes `--config-file .pypirc`: the project-root `.pypirc` holds the TestPyPI and PyPI API tokens, is gitignored and must never be committed. `twine` and `build` live in the repo `.venv` (the system Python refuses pip installs), so activate it first:
```bash
make dashboard       # npm install + npm run generate (builds src/bottler/dashboard/dist)
make package         # depends on `dashboard`; rm dist/build, python3 -m build
make test-publish    # package, then upload to testpypi
make test-upload     # upload existing dist/ to testpypi
make publish         # package, then upload to real PyPI (irreversible per version)
make upload          # upload existing dist/ to real PyPI
```

Run an example app (`examples/README.md` lists them: `hello_world`, `task_tracker`, `auth_hooks`, `mounts`, `plain_bottle`). `auth_hooks` has no `app.py` and runs via `bottler --dir examples/auth_hooks`; `mounts` and `plain_bottle` create their sqlite DBs on first run (gitignored):
```bash
cd examples/task_tracker && python3 app.py
```

Run the CLI locally without installing the console-script entry points:
```bash
PYTHONPATH=src python3 -m bottler.cli.app -d -r --sqlite
PYTHONPATH=src python3 -m bottler.cli.create
```
The `-d` flag serves the dashboard from `src/bottler/dashboard/dist`, which does not exist until you run `make dashboard` (or `npm run generate` in `client/`) at least once — it is not committed to git (see below) and `setupDashboard` prints a warning at startup if it's missing.

`PYTHONPATH=src python3 -m bottler.cli.app ...` works directly (`app.py` has an `if __name__ == "__main__": main()` guard) in addition to the installed `bottler` console-script entry point (from `pyproject.toml`).

Dashboard client (Nuxt 3/4 + Nuxt UI v4, in `client/`): its build output (`npm run generate`) is generated directly into `src/bottler/dashboard/dist` (see `nitro.output.publicDir` in `client/nuxt.config.ts`) and packaged via `MANIFEST.in`'s `graft src/bottler/dashboard/dist`. That directory is intentionally gitignored/not committed — `make dashboard` (or `make package`, which `make test-publish` and `make publish` depend on) builds it fresh instead. The Nuxt CLI needs Node >=20.12 (`node:util`'s `styleText`) and `nuxt typecheck` needs `vue-tsc` as a devDependency — both gaps surface as opaque errors if either is missing/too old.
```bash
cd client && npm install
npm run dev        # nuxt dev server
npm run generate   # static build -> writes directly into src/bottler/dashboard/dist
```

## Architecture

### Core class: `Bottler` (`src/bottler/core.py`)

`Bottler` extends `bottle.Bottle`. Its `__init__` wires everything together in order, with each feature independently toggleable and configurable via constructor args OR `bottler.toml` (toml values override constructor args — see `setup*` methods reading `self.cfg`):
1. `setupCors` — installs `CorsPlugin`; `cors` accepts a bare `True` for the original unrestricted `Access-Control-Allow-Origin: '*'` behavior, or `{"origins": [...]}` to echo back only an allowlisted requesting `Origin`
2. `setupSql` / `setupSqlite` — mutually exclusive (raises if both passed); installs `sqlPlugin`/`sqlitePlugin`, available to resources as an injected `db` cursor
3. `setupJwt` — installs `JWTPlugin`; auto-registers `GET/POST/OPTIONS /token` and `/users/current`. `jwt` defaults to `True` (not a fixed key): with no explicit `str`/`dict` key, a random `secrets.token_urlsafe(32)` secret is generated per process (printed as a warning, since it invalidates outstanding tokens on restart) rather than falling back to a hardcoded/guessable key.
4. `setupAuth` (if `gen_auth`, default `True`, and JWT is enabled) — looks for a project-root `auth.py` defining a callable `authenticate` and, if found, wires it up as the `/token` auth function via `setTokenAuthFunction` (same mechanism as calling it by hand, e.g. `examples/task_tracker/app.py`'s `authenticate`); a no-op if `auth.py` is absent, and a printed warning (falling back to the default always-succeeds `authFunc`) if it exists but has no callable `authenticate` — never a hard failure
5. `setupDashboard` — serves the built Nuxt SPA from `dashboard/dist` at `/dashboard`, and overrides the JWT token endpoint with `DashboardToken.authenticate` if no custom auth func was set
6. `setupRest` — installs the vendored `API` plugin (`plugins/rest.py`), auto-imports any `Resource` subclasses found in `./resources/*.py` (via `importResourcesFromFile`, using `importlib`), and always registers five built-in meta-resources: `AllResources` (`/_resources`), `DataTypes` (`/_datatypes`), `Config` (`/bottler_cfg`), `PythonResources` (`/_python_resources`), `ResourceRoles` (`/_roles`). Each of these five is passed through `_protectBuiltinResource`/`setRoles` and defaults to `roles = True` (any authenticated user) on every method except `OPTIONS` — these are schema/config/role-mutation endpoints, so unlike hand-authored or DB-generated resources (which are unprotected unless the project configures `roles` itself or sets `default_roles`), they're never silently wide open. `_protectBuiltinResource` calls `setRoles(..., use_default=False)`, so `default_roles` never applies to them. `resources.<name>.roles` in `bottler.toml` (keyed by `_resources`/`_datatypes`/`bottler_cfg`/`_python_resources`/`_roles`) still layers a more specific restriction on top via the normal `setRoles` mechanism. `dashboard_token`'s own `/dashboard/setup` bootstrap route is deliberately excluded (self-guarded via `isConfigured()` instead).
7. `createResForDB` (if `gen_db` and a DB is configured) — introspects every table in the connected database and auto-generates a CRUD `Resource` for each one that doesn't already have a route
8. `setupHooks` (if `gen_hooks`, default `True`) — runs last, after every route above (including `setupOpenApi`) is registered; looks for a project-root `hooks.py` defining a callable `configure(app)` and, if found, calls it with `self` — letting a project add routes/plugins/middleware or override anything `Bottler` itself just set up. A no-op if `hooks.py` is absent, and a printed warning if it exists but has no callable `configure` — never a hard failure, same contract as `setupAuth`.

`api_prefix` (constructor kwarg or top-level `bottler.toml` key, e.g. `"/api"`) prepends a fixed prefix to every route registered as part of the project's own API — hand-authored resources (`importResourcesFromFile`), auto-generated DB resources (`createResForDB`), and the JWT `/token`/`/users/current` endpoints (`setupJwt`) — via the `apiPath(path, prefix=None)` helper, applied at each of those call sites right before the route is registered. It never touches `EXCLUDED_PREFIXES`-covered routes (`/dashboard*`, `/openapi.json`, `/_resources`, `/_datatypes`, `/bottler_cfg`, `/_python_resources`, `/_roles`) — those back the bundled dashboard SPA, which calls them at fixed, unprefixed paths baked into its own build. A `Resource` subclass can override the app-wide prefix for just itself via a class-level `api_prefix` attribute (default `None` = inherit; e.g. `""` opts a resource out entirely, for something like a root-mounted static-file/SPA resource that needs to coexist with a prefixed API on the same app). Since `JWTPlugin.apply()` derives its token-path lookup key by flattening `route.rule` (stripping every `/`) on every request, `setupJwt`/`setTokenAuthFunction` rekey `self.jwt.token_paths` to match whichever flattened key the (possibly-prefixed) route actually resolves to (e.g. `"apitoken"` for `/api/token`) rather than leaving it keyed on the unprefixed literal `"token"` — this is the same rekeying `setupDashboard` already does by hand for its own `/dashboard/token` → `"dashboardtoken"`.

Any resource with an explicit `api_prefix` override is **registered last**, after every default-prefixed route (hand-authored, the five built-in meta-resources, and `createResForDB`'s DB auto-CRUD) — `importResourcesFromFile` appends `(resource, paths)` to `self._deferred_resources` instead of calling `self.rest.addResource(...)` immediately when `resource.api_prefix is not None`, and `__init__` drains that list via `_registerDeferredResources()` right after `createResForDB()`, before `setupOpenApi`. This exists because Bottle's router matches *dynamic* routes (anything with a `<param>`) in **registration order** — first match wins, not most-specific-match — so a root-mounted catch-all like `/<path:path>` (whose `.+?` pattern matches across `/`) can shadow a real, more-specific dynamic API route (e.g. `/api/<table>/<key>`) if it happens to register first. Hand-authored resources register via `importResourcesDir()`'s `os.listdir()`, which has **no defined ordering**, so without this deferral a catch-all-style resource would non-deterministically shadow other hand-authored resources' dynamic routes, and would *always* shadow every DB auto-CRUD dynamic route (`createResForDB` unconditionally runs after `setupRest`). Regression test: `test_deferredResource_catchAll_doesNotShadowDbAutoCrudRoute` in `tests/test_bottler.py`, using the `tests/resources/catchall_override_resource.py` fixture.

Config precedence: `bottler.toml` sections (`cors`, `rest`, `jwt`, `sqlite`, `sql`, `dashboard`, `openapi`, `api_prefix`, `default_roles`, `mounts`, `resources.<name>.paths`, `resources.<name>.roles`) are read in `__init__`/`setRoles`/`importResourcesFromFile` and take precedence over the values passed into the constructor. Two precedence subtleties, both intentional/covered by tests rather than bugs to fix:
- `default_roles` (constructor kwarg or top-level toml key; `True`, a list, or a comma string normalized by `_normalizeRoles`; stored as `self.default_roles`) is applied last in `setRoles`: for every method except `OPTIONS` whose route config still has no `roles` key after the class and `resources.<name>.roles` are considered. An explicit `false` in toml counts as a key, so it opts that method out. `_buildRoles` takes the app's `default_roles` as the fallback for unset methods, so the dashboard shows the effective value. Tests: `tests/test_default_roles.py`.
- `setRoles` *appends* toml roles onto a resource method's existing `roles` route config when one is already set (e.g. the built-in resources' `roles = True` default, or a hand-authored resource declaring its own `roles`), and only cleanly *overrides* when no `roles` key exists yet. Appending onto an existing `bool` (e.g. `True += ["admin"]`) raises `TypeError`, which is caught, printed, and left as-is — so a toml `resources.<name>.roles` override is silently inert against a resource that already hardcodes a bool `roles` (see `test_setRoles_preexistingBoolRoles_printsAndSkips`).
- `resources.<name>.paths` in toml *replaces* the default route(s) entirely for a hand-authored resource (`importResourcesFromFile`), but only *appends* to the always-present canonical CRUD routes for a DB-generated one (`createResForDB`) — the latter deliberately guarantees `/<table>/<key>` always exists, since the generated `get`/`put`/`patch`/`delete` functions depend on that route param being present.

### Auto-generated DB resources: `resource_factory.py`

`createResource(name, fields, sql)` dynamically builds a `Resource` subclass per DB table:
- `key` = the column flagged as primary key in the introspected field list. `createResForDB` skips (with a printed message) any table where no field has `key == 1` before calling `createResource` — a table without a detected PK crashes `createResource` itself (its generated `post`/`patch` functions reference `ChildResource.key` unconditionally), so this guard is required; `getDBTables()`'s sqlite listing query already excludes PK-less tables via `sql LIKE '%PRIMARY%'`, but the MySQL listing query does not, which is why the guard lives in `createResForDB` rather than relying on introspection alone.
- `get` supports filtering by any query param (`LIKE`), a single-row lookup by primary key, a `levels` param for following foreign keys N levels deep via `getRefs` (which discovers FK relationships and recursively inlines referenced rows), and nested-resource routes like `/<ref_table>/<ref_id>/<table>`. Query-param filtering only binds the *values*; the *keys* (arbitrary query-string names) are validated against `field_names` (the table's real columns, captured at resource-creation time) before being concatenated into the `WHERE ... LIKE ...` clause, and rejected with a 400 if any key isn't a real column — this closes what was otherwise a SQL-injection-via-filter-key hole. `getRefs` branches on `bind_char` for FK discovery: MySQL uses `information_schema` (`FOREIGN_KEY_SQL`), sqlite uses `PRAGMA foreign_key_list(table)` — both paths normalize into the same 4-key dict shape. One known limitation remains: the nested-route branch in `get()` matches an FK by referenced-table name only, so a table with more than one FK to the same referenced table (e.g. a self-referencing `predator`/`prey` pair both pointing at `animals`) is ambiguous — it always resolves to whichever FK is discovered first, which may not be the column the caller meant.
- `post`/`put`/`patch` handlers are generated at class-creation time via `createFunction`, which builds a function via `exec()` with a parameter list matching the table's actual columns (so each resource's method signature reflects its schema) and dispatches to `_doPost`/`_doPut`/`_doPatch`. The route `createResForDB` registers for `put`/`patch` is `/<table>/<key>` — a URL param literally named `key` — while the table's real primary-key column can have any name (e.g. `id`); `createFunction` takes a `key_param` argument that renames that one positional arg to `key` in the generated outer signature (matching the route and satisfying the `API` plugin's required-field check) while still passing it through to `_doPost`/`_doPut`/`_doPatch` under the real column name, mirroring how `get`/`delete` already hardcode their own parameter as literally `key` and translate internally via `self.key`. `_doPost`/`_doPut`/`_doPatch`/`delete` all funnel their mutation through a shared `_runMutation(action)` helper, so a unique-constraint violation is always a clean 422 (not just on create) and any other exception is a 500 — one shared try/except instead of four near-identical copies. `_doPut`/`delete` perform a real full-replace update / row delete.
- `bind_char` is `%s` for MySQL (`pymysql`) vs `?` for SQLite — the same code paths otherwise handle both DB backends. `getDBCursor`/`getDBTables` in `core.py` pick the backend via `if self.sqlite: ... elif self.sql: ... else: raise` (not duck-typing/`try-except` — a bare except there used to silently mask a "neither configured" misuse as a MySQL connection attempt).

### Meta/admin resources: `resources.py`
`AllResources`, `DataTypes`, `Config`, `PythonResources`, `ResourceRoles` back the dashboard UI — they let the dashboard list tables, create tables (`POST /_resources`), and patch a resource's `roles`/`paths`/`fields` (schema alterations), which round-trip through `Bottler.alterDBTable`/`updateRoles`/`updatePaths`/`saveConfig`. `alterDBTable` validates every identifier it's given (table/column names against `resource_scaffold.NAME_RE`, column types against `SQLITE_TYPES`/`MYSQL_TYPES`, default values against a conservative literal pattern) before concatenating them into DDL, since none of sqlite3/pymysql support bind parameters inside `ALTER TABLE`. MySQL now supports `ADD COLUMN`/`RENAME COLUMN` (mirroring sqlite; `RENAME COLUMN` needs MySQL >= 8.0 / MariaDB >= 10.5.2) in addition to the pre-existing `DROP COLUMN` — previously add/rename against a MySQL-backed project was a silent no-op that still reported success. `AllResources.patch`/`PythonResources.patch`/`ResourceRoles.patch` share their `roles`/`paths`/`remove_path` dispatch and method-name normalization via module-level `_applyRolesOrPaths`/`_normalizeMethod` helpers rather than three copies of the same branches.

### OpenAPI spec generation: `openapi.py`
Builds a full OpenAPI 3.0.3 spec at runtime by walking `app.routes` — inferring path params, DB-table request/response schemas via introspection, marking `security` requirements on JWT-protected routes, and grouping routes into `tags`. Served for the dashboard's interactive API docs UI (see the `client/` section below).

### Testing (`tests/`)
`unittest`-based, one file per plugin/module: `test_bottler.py` (core `Bottler`, config precedence, DB introspection/DDL), `test_resource_factory.py`, `test_resources.py`, `test_rest.py`, `test_jwt.py`, `test_sql.py`, `test_cors.py`, `test_dashboard_token.py`, `test_openapi.py`, `test_resource_scaffold.py`. Shared helpers:
- `_paths.py` — idempotent `os.chdir` into `tests/`, imported (`import _paths  # noqa: F401`) at the top of every test module instead of a single hardcoded `os.chdir("tests")` at import time.
- `mysql_mock.py` — `make_mysql_cursor()`/`patch_pymysql_connect()` build a `MagicMock(spec=pymysql.cursors.DictCursor)` (the `spec=` is required — `bottler.getDBTables()` does `isinstance(db, pymysql.cursors.Cursor)` with no fallback branch) whose `execute()` returns an int by default, matching real pymysql/DBAPI rowcount semantics (unlike `sqlite3.Cursor.execute()`, which returns `self`) — this is what's needed to exercise `resource_factory.py`'s MySQL-only fallback branches (`except: rows = db.fetchall()`, `except AttributeError: last_row_id = db.lastrowid`).
- `db_fixtures.py` — `temp_sqlite_copy()` copies the committed `tests/resources.db` to a throwaway tempfile for any test that mutates rows/schema. **`temp_cfg_copy()` (copies `bottler.toml` verbatim) is NOT sufficient isolation on its own for DB-mutating tests** — the committed toml sets `sqlite = "resources.db"`, and toml values always override constructor args, so a `Bottler(cfg_file=<copied toml>, sqlite=<tmp_db>, ...)` still silently operates on the real shared fixture (this bit a test during development and corrupted the committed fixture until caught via `git diff`/`git checkout`). Use `temp_cfg_pointing_at(tmp_db_path)` instead for any test that both mutates the DB and needs a writable cfg file (e.g. exercises `saveConfig`/`updateRoles`/`updatePaths`).
- `NONEXISTENT_CFG`-style sentinel filenames (a `cfg_file` that doesn't exist) are used throughout to force `self.cfg = {}` and let constructor args take full effect, bypassing `bottler.toml`'s override — the standard pattern for testing non-default `cors`/`rest`/`jwt`/`sqlite`/`sql`/`dashboard` configurations.

After any test run, verify `tests/resources.db` is still the committed version (`git status --short tests/resources.db`) — even read-only sqlite3 connections can touch a few internal bookkeeping bytes without changing row/schema content (harmless, but `git diff --stat` will show a nonzero byte diff; `git checkout -- tests/resources.db` restores it).

### Live reload: `reload.py`
A near-empty module (`# Used to force reload`) that `Bottler.reloadServer()` rewrites to touch its mtime — this is the mechanism that triggers bottle's `reloader=True` process restart after the dashboard changes config/schema at runtime.

### CLI scripts (`src/bottler/cli/`)
- `app.py` — the `bottler` entry point; parses CLI flags (`--dir`, `--jwt`, `--sqlite`, `--dbhost/--dbname/--dbuser/--dbpass`, `--cors`, `-r`, `-d`), chdir's into `--dir` first (if given) so `bottler.toml`/`resources/` resolve relative to it rather than the invoking shell's cwd, builds `Bottler(**kwargs)`, retries on `Exception` with a 5s backoff (but exits on `sqlite3.OperationalError`/`pymysql.err.OperationalError`), and cleans up the temp SQLite file on exit if `--sqlite` was used with no path.
- `create.py` — the `bottler-create` entry point; interactively scaffolds a new project directory (`resources/` subfolder + `bottler.toml`, copying `hello_world.py` as a starter resource, and unconditionally writing a reject-all `auth.py` stub via `auth_scaffold.writeAuthFile` — see below), optionally creating a SQLite DB file or prompting for SQL connection details.
- `bottler-resource` — the entry point for `resource()` in `create.py`: prompts for a resource name, validates it against `resource_scaffold.NAME_RE` (lowercase snake_case), writes `resources/<name>.py` from the `resource_scaffold.render()` template, and appends a default `[resources.<name>]` section (with `paths = ["/<name>", "/<name>/<key>"]`) to the project's `bottler.toml`.

### User-facing resource convention
A user project defines `Resource` subclasses (from the internal `bottler.plugins.rest` module, re-exported as `bottler.Resource`) in a top-level `resources/` folder; `Bottler` scans that folder automatically unless `gen_res=False`. Each resource implements `options/get/post/put/patch/delete`; the vendored `API` plugin handles dispatch and injects `db` when a SQL/SQLite plugin is installed.

`setupRest`'s `importResourcesDir`/`importResourcesFromFile` (`core.py`) load `resources/` as a real (namespace) package via `importlib.import_module("resources.<name>")`, not by `exec`-ing each file in isolation — this lets resource files use relative imports (`from . import helper`) for sibling modules in `resources/`, or absolute imports of other project modules (`from myproject.utils import x`), since the project root (`os.getcwd()`) is temporarily added to `sys.path` for the duration of the scan. Afterwards, the added `sys.path` entry (if any) and every `"resources"`/`"resources.*"` entry in `sys.modules` are removed again, so repeated `Bottler()` instantiations against different projects in the same process (tests, the CLI's retry-on-exception loop) always re-read resource files from disk instead of serving another project's cached modules. `setupAuth`'s equivalent cleanup for `auth.py` (below) uses the identical temp-sys.path-insert + sys.modules-entry-removal *mechanism*, but the two aren't fully equivalent in what they guard against: `auth` is an ordinary module (first match wins when walking `sys.path`), while `resources` is a PEP 420 namespace package whose `__path__` is the *union* of every `resources/` directory found across all of `sys.path`, not just the one just-inserted project root — so a stale, unrelated `resources/` directory left on `sys.path` by something else in the same long-lived process could get merged into the namespace package in a way a plain-module import structurally can't reproduce. Narrow edge case (same-process, multiple projects, an unrelated stale `sys.path` entry), not something either cleanup routine can fully close.

### Package mode and mounts (`package`, `base_dir`, `mounts`, `mounted`)
- `Bottler(package=..., base_dir=...)` imports resources from `<package>.resources` via `importPackageResources` (`pkgutil.iter_modules`, sorted) instead of `./resources`. `cfg_file` defaults to `<base_dir>/bottler.toml`. `setupAuth` is skipped and `setupHooks` calls the package's own `configure(app)` (from its `__init__`) instead of `hooks.py`.
- Package modules are **not** purged from `sys.modules`, so their classes are reused across builds. `_resetRouteConfig` snapshots each class's own route config (`_bottler_route_cfg`, set once per class) and restores it before `setRoles`, so toml roles don't pile up (`+=`) across builds.
- `mounts` (toml table or constructor dict; entry = package name or `{package, base_dir}`) is handled by `setupMounts`, which runs after `createResForDB` and before `_registerDeferredResources` (so a parent catch-all SPA route can't shadow mounted routes). Each entry builds a child with `mounted=True` and calls `self.mount(apiPath("/<name>/"), child)`. The trailing slash matters: Bottle 0.13's `_mount_app` then merges the child's routes into the parent router while keeping `route.app = child`, so **the child's plugins run** (its own SQL plugin and `db`, JWT, CORS). That is how one process serves several databases despite the one-DB-per-app rule.
- In a child (`mounted=True`), `_cfgValue` ignores the child toml for `MOUNT_INHERITED` (`jwt`, `cors`, `rest`, `dashboard`, `openapi`, `api_prefix`); the parent passes its resolved `_jwt_cfg`/`_cors_cfg`/`default_roles`. `setupJwt` clears `token_paths` and registers no `/token` in a child. A child never mounts further.
- `base_dir` resolves against the parent's cfg file folder (cwd when `cfg_file` isn't a string). Mount names must match `[A-Za-z0-9_-]+`. Tests: `tests/test_mounts.py` (temp packages on `sys.path`, one sqlite DB each).

### User-facing auth convention
`setupAuth` (`core.py`) mirrors the `resources/` convention above but for a single top-level module instead of a package: it looks for `auth.py` at the project root (`os.getcwd()`) defining a callable `authenticate(username=None, password=None, **kwargs)` (same signature/return-value contract as the argument to `setTokenAuthFunction` — a truthy dict payload on success, encoded into the issued JWT, or falsy to reject) and, when found, calls `setTokenAuthFunction(authenticate)` internally. It's opt-out via `gen_auth=False` (constructor-only, not toml-overridable, same as `gen_res`/`gen_db`) and is a no-op whenever JWT itself is disabled. Uses the identical temporary-`sys.path`-insert + `sys.modules["auth"]` cleanup as `importResourcesDir`, scaled to one module name instead of a `resources.*` prefix match, for the same repeated-instantiation-across-projects reason. `auth.py`/`authenticate` are fixed names, not currently configurable via `bottler.toml` — a deliberate simplification for now, deferred rather than ruled out.

### User-facing hooks convention
`setupHooks` (`core.py`) mirrors the `auth.py` convention above but for arbitrary post-setup customization instead of auth: it looks for `hooks.py` at the project root (`os.getcwd()`) defining a callable `configure(app)` and, when found, calls `configure(self)` directly — no return-value contract, since it's a side-effecting hook rather than a value provider. It runs last in `__init__`, after `setupOpenApi`, so `configure(app)` sees every route `Bottler` itself registers (hand-authored resources, DB auto-CRUD, `/token`, the dashboard, `/openapi.json`) and can freely add its own routes/plugins/middleware via the normal `Bottle`/`Bottler` API (`app.route(...)`, `app.install(...)`, `app.rest.addResource(...)`, etc.) or override what's already there. It's opt-out via `gen_hooks=False` (constructor-only, not toml-overridable, same as `gen_res`/`gen_db`/`gen_auth`) and, unlike `setupAuth`, does not depend on JWT being enabled. Uses the identical temporary-`sys.path`-insert + `sys.modules["hooks"]` cleanup as `setupAuth`, for the same repeated-instantiation-across-projects reason. Works identically under the CLI, a hand-rolled `app.py`, and a WSGI deploy (`wsgi.py`'s module-level `application = Bottler(...)`) — `setupHooks` fires inside `__init__` regardless of what constructs the instance, as long as the process cwd is the project root when it runs. `hooks.py`/`configure` are fixed names, not currently configurable via `bottler.toml` — same deliberate simplification as `auth.py`/`authenticate`.

### Dashboard client (`client/`)
Nuxt 3/4 SPA (`ssr: false`, statically `nuxt generate`d and served by `Bottler` itself — no Node/Nitro server at runtime) using Nuxt UI v4 + Tailwind v4. Uses Nuxt 4's `app/`-as-srcDir layout: pages/components/composables/layouts/middleware all live under `client/app/`, and **`app.config.ts` must live at `client/app/app.config.ts`, not the project root** — Nuxt resolves it relative to the app srcDir, and a root-level copy is silently ignored (no error, it just falls back to defaults). `@nuxtjs/auth-next`/`@nuxtjs/axios` (unmaintained on Nuxt 3/4) are replaced by hand-rolled composables in `client/app/composables/`: `useAuth.ts` (JWT in a reactive cookie, against `Bottler`'s `/token` endpoint), `useApi.ts` (shared `$fetch.create` instance, attaches the bearer token, logs out only on 401 — not 400, since `PUT /bottler_cfg` legitimately 400s on bad TOML), `useConfigStore.ts` (TOML round-trip via `smol-toml`), `useResourcesStore.ts`, `useToastError.ts`. Pages under `client/app/pages/` (`config.vue`, `resources/index.vue`, `resources/[id].vue`, `login.vue`, `index.vue`, `setup.vue`, `python-resources/index.vue`, `python-resources/[name].vue`) map directly to the `_resources`/`bottler_cfg` meta-endpoints above (the `python-resources` pages list/inspect the hand-authored `Resource` subclasses in a project's `resources/` folder, as opposed to the auto-generated DB resources under `resources/`). `api-explorer.vue` renders the spec served by `openapi.py` via a hand-rolled Nuxt module under `client/modules/`: `nuxt-swagger-ui` (global client-only `<SwaggerUIViewer>` component), which wraps the third-party Swagger UI library. Custom brand colors and fonts live in `client/app/assets/css/main.css`: Tailwind v4's `@theme` block tree-shakes any custom token not referenced by a literal utility class in a template, so colors only ever consumed via `var(...)` at runtime (as Nuxt UI's `ui.colors` aliases in `app.config.ts` do) must go in `@theme static` instead, or they silently vanish from the compiled CSS. It's a separate npm project — not part of the Python package's dependency/test chain, only its build output is bundled into the wheel.

`client/nuxt.config.ts` sets `components: [{ path: '~/components', pathPrefix: false }]` — every template in this app references subdirectory components by their bare filename (`<ResourceDataTable>`, `<PageHeader>`, ...) rather than Nuxt's default directory-prefixed name (`ResourcesResourceDataTable`, `BasePageHeader`, ...). Without `pathPrefix: false`, any component whose filename doesn't start with its parent directory's PascalCase name silently fails to resolve at runtime (no build error) — this is what broke the resource-detail page (`ResourceDataTable`/`ResourceEditDialog` under `components/resources/`) before the fix. Keep new subdirectory components' bare filenames unique across the whole `components/` tree, since prefixing is now off globally.

`client/app/components/base/` holds shared UI primitives reused across pages: `PageHeader` (title/description + `#actions` slot), `EmptyState` (icon/message + `#action` slot), `StatCard`, `BrandMark` (the dot+wordmark, `size="sm"|"lg"`), `BrandScreen` (full-viewport shell wrapping `BrandMark` — used by `login.vue`/`error.vue`), and `LoadingRows` (skeleton placeholders, `variant="list"|"stat"|"card"`) in place of plain "Loading..." text. `client/app/utils/humanize.ts` exports `humanizeKey()` for turning raw DB/pragma keys (`dflt_value`, `notnull`, `cid`, ...) into readable labels in `ResourceEditDialog`/`ResourceDataTable`.

`client/app/layouts/default.vue` renders a `UBreadcrumb` in the navbar's `#title` slot (driven by each page's `definePageMeta({ title: '...' })`, with a "DB Resources" segment prepended for `/resources/[id]` routes) instead of a static title, and mounts a `UDashboardSearch`/`UDashboardSearchButton` Cmd/Ctrl+K command palette seeded from the sidebar nav items plus `useResourcesStore()`'s resource list.
